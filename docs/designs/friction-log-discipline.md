### D5 — events.jsonl is PERMANENT FOUNDATION

- Schema includes `"v": 1` field, locked Rust struct, `SCHEMA.md` doc beside the file (user committed to forever-foundation, so docs justified).
- Forever-useful for weekly retros, agent-quality dashboards, friction-driven roadmap.
- **Concurrency:** Multiple tokio tasks may emit concurrently. Mandate `tokio::sync::Mutex<File>` wrapping the append handle in `friction_emitter`, OR per-write `OpenOptions::new().append(true)` with kernel-atomic append (POSIX `O_APPEND` writes <PIPE_BUF=4096 bytes are atomic; v:1 events are <500 bytes, well within the limit). Spec'd approach: per-write open with `O_APPEND` (simpler, no shared state, no mutex contention). **Darwin/APFS caveat:** macOS is not strictly POSIX-conformant on this guarantee — verified empirically via the concurrent-write test in the Verification Plan (50 parallel emits, count lines == 50, no malformed JSON). If that test fails on Darwin, fall back to `tokio::sync::Mutex<File>`. Document the chosen path in SCHEMA.md.

#### 1. friction_emitter (Step 3)
`crates/services/src/services/friction_emitter.rs`. One `emit(event, venture, workspace_id, metadata)` helper.

**Schema (locked v:1):**
```jsonl
{"v": 1, "ts": "2026-04-28T17:23:01Z", "event": "snake_case_string", "venture": "string|null", "workspace_id": "32-char-hex|null", "metadata": {}}
```

**Event enumeration + dedup rule (closes "what counts as one event"):**

| Event | Trigger point (single call site) | Dedup rule |
|-------|----------------------------------|------------|
| `workspace.create` | After successful row insert in workspaces table | One per persisted row, even if upper handler retries |
| `dispatch.fire` | After dispatch_log row insert | One per dispatch_log.id |
| `supervisor.trip` | After auto_approval status flips to non-default | One per auto_approval row state change |
| `mail.send` | After mail row insert (any kind) | One per mail.id (no dupe for fan-out) |
| `automation.fire` | After automation_rules execution row insert | One per execution row |
| `auto_approval.grant` | When supervisor outcome = "approved" | One per supervisor decision; not per check |
| `auto_approval.deny` | When supervisor outcome = "denied" | One per supervisor decision; not per check |

**Source rules:**
- `workspace_id`: hex-encoded SQLite BLOB UUID from `workspaces.id` (16 bytes → 32 hex chars). Use `hex::encode(workspace.id)`. Null only when no workspace context exists (e.g., supervisor-level events not tied to a workspace).
- `venture`: read from `workspaces.venture` column at emit time. Null if column NULL.
- `ts`: `chrono::Utc::now().to_rfc3339()`.

**Concurrency:** Per-write `OpenOptions::new().create(true).append(true).open(path)` with `O_APPEND` semantics. POSIX guarantees atomic appends for writes < PIPE_BUF (4096 bytes); v:1 events are < 500 bytes. No mutex needed. Document this in SCHEMA.md.

**Failure mode:** Swallows `io::Error` to stderr via `tracing::error!`, never panics. Cockpit must not crash because the log can't be written.

**Instrumentation point caveat:** Codex T4 prefers API/dispatch boundary over per-handler. Decision deferred to /plan-eng-review — they can flip to a single boundary call if cleaner. Plan defaults to per-handler for explicitness; eng review can refactor.

#### E-AUTO-2: Concurrency strategy — flagged as TASTE DECISION for final gate

Codex correctly identified that the per-write `O_APPEND` claim is wrong: **PIPE_BUF guarantees apply to pipes, not regular files.** O_APPEND protects file offset (no two writes will overlap in offset), but does NOT protect record integrity if a single Rust `write_all` call gets split across syscalls under tokio. AND: `gencap log` is a separate process from the server, so any in-process Mutex<File> is insufficient.

Two viable architectures:

**Option A: JSONL-first with cross-process advisory lock + single-syscall guarantee**
- One pre-serialized buffer including newline, single `write_all` call
- `flock(LOCK_EX)` advisory lock around each emit (cross-process safe)
- Slower under contention; more code (lock acquisition + release on panic)
- Rust + shell script (`gencap log`) both must use the same locking pattern

**Option B: SQLite as event store, JSONL export at day-3**
- Add `friction_events` table to existing vibe-kanban SQLite DB
- Schema: `id BLOB PK, ts TEXT, event TEXT, venture TEXT NULL, workspace_id BLOB NULL, metadata JSON`
- Reuses existing SQLx infrastructure (DRY, P4)
- SQLite handles concurrency natively across processes
- JSONL is exported at day-3 reread (`scripts/export-events.sh`)
- Schema versioning = ALTER TABLE migrations (locked-in pattern)
- Eliminates the entire concurrency-spec debate

**Recommendation: Option B.** Reuses what exists (P4 DRY), eliminates a class of bugs (P3 pragmatic), schema versioning is well-trod (P5 explicit). The "events.jsonl is permanent foundation" decision (D5) re-aligns nicely: SQLite IS the foundation; JSONL is the export format.

**Marked as TASTE DECISION because the user already committed to JSONL-as-foundation in D5.** Final gate gets to flip to SQLite or stay with JSONL+lock.

```
  log [--quick "msg"]  Append a friction-log entry (interactive prompts; --quick for terse)
  status               Show experiment status: day N of 3, last entry/event timestamps,
                       counts by severity, time until day-3 reread
  teardown             Day-4 cleanup: launchctl unload, remove CLAUDE.md banner,
                       archive friction-log.jsonl + events store with date stamp
  extend --days N      Mid-experiment extension: shifts day-3 deadline by N days,
                       updates CLAUDE.md banner with new deadline, re-arms launchd

Environment:
  GENCAP_FRICTION_ENABLED=0   Kill switch — emitter no-ops (no rebuild needed)

Examples:
  gencap log                              # interactive prompt
  gencap log --quick "model retry storm"  # 1-line capture
  gencap status                           # current state
  gencap extend --days 2                  # add 2 days
  gencap teardown                         # end experiment
```

#### DX-AUTO-5: Schema versioning policy

Add explicit policy to `friction-log-schema.md`:

```markdown
## Versioning Policy

- **Minor (additive):** New fields can be added without bumping `v:`. Readers must accept unknown fields.
- **Major (breaking):** Field removal or rename requires `v:N+1`. Writers MUST write to BOTH `v:N` and `v:N+1` paths during a transition window of ≥7 days. Readers MUST accept any `v:M ≤ N` (read-forward compatibility).
- **Read-write version matrix:**
  - v:1 reader → reads v:1 only
  - v:1 writer → writes v:1 only
  - v:2 reader → reads v:1 AND v:2 (during transition)
  - v:2 writer → writes v:1 AND v:2 (during transition)
- **Deprecation:** v:N is deprecated 30 days after v:N+1 stable. Removed 90 days after.
- **SQLite path (Option B at gate):** Schema migrations via standard SQLx migrations. ALTER TABLE for additive; new table + view for breaking.
```

```bash
#!/usr/bin/env bash
```
